# Standup API：会場の削除 仕様

## 1. 概要

Standup Spotに登録されている会場の削除処理を行う。

会場がイベントで使用されているかどうかに応じて、物理削除または非表示化を行う。

- **API:** `services/standup/venue_delete.php`
- **HTTPメソッド:** `POST`
- **データベース:** `standup_venues`、`standup_venue_managers`、`standup_event_candidates`
- **リクエスト形式:** JSON
- **レスポンス形式:** JSON

## 2. 削除方針

会場の削除方法は、イベントでの使用状況によって決定する。

| イベントでの使用状況 | 処理 | 理由 |
|---|---|---|
| 未来のイベントで使用中 | 削除不可 | 開催予定のイベントへの影響を防ぐ |
| 日時未定のイベントで使用中 | 削除不可 | 開催予定となる可能性のあるイベントへの影響を防ぐ |
| 過去イベントで使用された履歴がある | 非表示化 | 過去イベントの会場情報を保持する |
| イベントで使用された履歴がない | 物理削除 | 不要な会場データを削除する |

### 2.1 物理削除

イベントで使用された履歴がない会場は、`standup_venues` からレコードを物理削除する。

`standup_venue_managers.venue_id` には外部キーの `ON DELETE CASCADE` が設定されているため、関連する管理者レコードも自動的に削除される。

### 2.2 非表示化

過去イベントで使用された履歴がある会場は、レコードを物理削除せず、次のように状態を変更する。

`status = 'inactive'`

会場情報をDBに残すことで、過去イベントとの関連を維持する。

非表示化された会場は、本APIによる削除処理の対象外となる。

## 3. API共通仕様

### 3.1 リクエスト

HTTPメソッドは `POST` のみ許可する。

リクエストボディはJSON形式とし、削除対象の会場IDを指定する。

```json
{
  "id": 123
}
```

`id` は正の整数で指定する。JSONデコード後の値が整数型でない場合や、1未満の場合はエラーとする。

### 3.2 認証・利用条件

次の条件を満たす必要がある。

1. ログインしていること。
2. `users.status = 'active'` であること。
3. Standupの有効なコメディアン、または有効な会場管理者ロールを持っていること。

有効なコメディアンとは、Standupの有効な `comedian` ロールを持ち、かつ有効なコメディアンレコードが存在するユーザーを指す。

## 4. 削除権限

削除対象の会場に、有効な担当管理者が存在するかどうかによって削除権限を判定する。

### 4.1 有効な担当管理者がいる場合

次の両方を満たすユーザーのみ削除できる。

- Standupの有効な `venue_manager` ロールを持っている。
- 対象会場の有効な担当管理者として登録されている。

有効な担当管理者とは、`standup_venue_managers.status = 'active'` のレコードによって対象会場に割り当てられているユーザーを指す。

### 4.2 有効な担当管理者がいない場合

次のいずれかを満たすユーザーが削除できる。

- 有効なコメディアンである。
- 有効な `venue_manager` ロールを持っている。

対象会場に有効な担当管理者がいない場合は、会場管理者ロールを持つユーザーであれば、対象会場への個別の管理者割り当てがなくても削除できる。

### 4.3 削除対象の状態

削除対象の会場は、存在しており、かつ `status = 'active'` である必要がある。

存在しない会場、またはすでに非表示化された会場は削除できない。

## 5. イベントの使用状況判定

イベントでの使用状況は、`standup_event_candidates` テーブルの `venue_id` を基準に判定する。

### 5.1 未来または日時未定のイベント

次のいずれかに該当するイベントで会場が使用されている場合、削除を拒否する。

- `COALESCE(start_at, open_at) >= NOW()`
- `start_at IS NULL AND open_at IS NULL`

つまり、`start_at` が設定されている場合は `start_at`、設定されていない場合は `open_at` を基準に判定する。両方が未設定の場合は日時未定として扱う。

該当するイベントが存在する場合、会場の状態は変更せず、エラーを返す。

### 5.2 過去イベントの使用履歴

未来または日時未定のイベントで使用されていないことを確認した後、`standup_event_candidates` に対象の `venue_id` が存在するか確認する。

- 履歴が存在する場合：`status = 'inactive'` に変更する。
- 履歴が存在しない場合：会場レコードを物理削除する。

## 6. 処理フロー

1. HTTPメソッドが `POST` であることを確認する。
2. DB接続を確立する。
3. ログイン状態とユーザーの有効性を確認する。
4. 有効なコメディアンまたは会場管理者ロールを確認する。
5. JSONリクエストから `id` を取得し、形式を検証する。
6. トランザクションを開始する。
7. 対象会場をロックして取得し、存在と有効状態を確認する。
8. 有効な担当管理者の有無を確認する。
9. 削除権限を判定する。
10. 未来または日時未定のイベントで使用中でないことを確認する。
11. イベントでの使用履歴を確認する。
12. 履歴があれば非表示化し、なければ物理削除する。
13. トランザクションをコミットする。
14. 処理結果をJSONで返す。

途中でエラーが発生した場合、トランザクションが開始済みであればロールバックする。

## 7. 成功レスポンス

### 7.1 物理削除

```json
{
  "success": true,
  "id": 123,
  "action": "deleted"
}
```

イベントで使用された履歴がない場合に返す。

### 7.2 非表示化

```json
{
  "success": true,
  "id": 123,
  "action": "deactivated"
}
```

過去イベントで使用された履歴がある場合に返す。

### 7.3 レスポンス項目

| 項目 | 説明 |
|---|---|
| `success` | 成功時は `true` |
| `id` | 削除または非表示化した会場ID。数値 |
| `action` | 実行した処理。`deleted` または `deactivated` |

本APIは、削除後の会場情報全体を返さない。

## 8. エラーレスポンス

エラー時は次の形式で返す。

```json
{
  "success": false,
  "error": "エラーメッセージ"
}
```

| HTTPステータス | 主な発生条件 |
|---|---|
| `400 Bad Request` | 会場IDの形式不正、未来または日時未定のイベントで使用中 |
| `401 Unauthorized` | 未ログイン、ユーザーが無効 |
| `403 Forbidden` | ロール不足、対象会場の削除権限不足 |
| `404 Not Found` | 対象会場が存在しない、または非表示状態 |
| `405 Method Not Allowed` | POST以外のリクエスト |
| `500 Internal Server Error` | DBエラーなどの予期しない内部エラー |

### 8.1 主なエラーメッセージ

| メッセージ | HTTPステータス |
|---|---|
| `Invalid venue id` | 400 |
| `Venue not found` | 404 |
| `Forbidden` | 403 |
| `Venue is used by a future or undated event` | 400 |
| `Internal server error` | 500 |

エラー時は `success: false` とし、成功時の `id` および `action` は返さない。

## 9. トランザクションと整合性

会場のロック取得、権限確認、イベントの使用状況確認、非表示化または物理削除をトランザクション内で処理する。

エラー時はロールバックすることで、途中までの更新が残らないようにする。

物理削除時は外部キー制約によって管理者レコードも削除される。

## 10. 補足事項

- 会場の登録・編集は `venue.php` で行い、削除は本API `venue_delete.php` で行う。
- 削除対象は有効状態の会場に限る。
- 未来または日時未定のイベントで使用中の会場は削除できない。
- 過去イベントの履歴がある会場は、物理削除せず非表示化する。
- イベントの使用履歴がない会場は物理削除する。
- 会場の物理削除に伴い、関連する管理者レコードも削除される。
